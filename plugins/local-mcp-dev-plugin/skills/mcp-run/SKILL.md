# 사내 MCP 실행 = 개발감사 → MCP 를 직접 띄워 툴 부르기

## 지금 상황 — 먼저 읽는다
- 이 회사의 Claude 는 관리자가 승인한 MCP 만 붙인다(조직 허용 목록). **개발 중인 MCP 는 이 Claude 에 MCP 로 붙일 수 없다.** `.mcp.json`·`claude mcp add`·설정 파일로 붙이려 하지 않는다(막히고, 회사 규칙 위반이다).
- 대신 키트의 시험 도구(mcp-test)가 MCP 를 이 PC 에서 직접 띄워 MCP 프로토콜(stdio)로 `tools/list`·`tools/call` 을 보내고 응답을 그대로 돌려준다.
- 그러니 **MCP 가 이 세션에 붙어 있는 것처럼 행동한다.**
  - 툴이 무엇이 있는지 알고 싶으면 → `test tools` 로 툴 목록(이름·설명·입력 스키마·annotations)을 본다.
  - 사용자가 "이 MCP 로 ○○ 해줘", "툴 불러봐"라고 하면 → 맞는 툴과 인자를 스스로 골라 `test call <툴> --args-file …` 로 부르고, 돌아온 결과(content)를 MCP 툴 결과로 여기고 답한다.
  - 툴 설명·스키마만 보고 고를 수 있는지도 본다 — 코드를 알아서 부를 수 있었지만 설명만으로는 헷갈리겠다 싶으면 툴 설명을 고친다(배포 뒤에는 다른 사람의 Claude 가 설명만 보고 고른다).
- 돌아온 결과가 기대와 다르면 코드를 고치고, 검사를 다시 통과시킨 뒤 다시 부른다.
- 사용자가 "시간 어디서 걸렸어" 류로 물으면 `.kit/log/` 의 최근 기록(JSON)을 읽는다 — `timeline` 은 [시작부터 초, 출력 줄] 목록이고, 3초 넘게 걸린 git·자격 증명·키트 호출은 `(걸린 시간 N초 — 무엇)` 줄로, mcp-test 단계는 `[N초]` 머리로 남는다. 단계 × 걸린 시간 표로 보여 주고 가장 긴 곳을 짚는다. 추정하지 말고 기록에 있는 숫자만.
- 스크립트(kitdev) 명령이 실패하면 그 명령 · 출력 · PC 상태(OS · Node · git · 프록시 · 플러그인 판)가 `.kit/log` 에 남고 사내 키트에도 보내진다(키트 관리자가 원인을 찾는 데 씀 — 비밀값처럼 보이는 것은 가려짐). 출력 끝의 '사내 키트에 보냈습니다 — 기록 <id>' 줄이 나오면 사용자에게 그 번호를 알려 주고, 관리자에게 물을 때 이 번호를 대면 된다고 말한다.

스크립트: `"<node>" "${CLAUDE_PLUGIN_ROOT}/scripts/kitdev.mjs"`
(치환되지 않았으면 이 스킬의 Base directory 기준 `../../scripts/kitdev.mjs`)

샌드박스 밖에서 실행: Codex 처럼 명령을 자기 샌드박스 안에서 돌리는 도구에서는 `node.ps1`·`node.sh`·`kitdev.mjs` 명령을 처음부터 샌드박스 밖 실행(Codex: 승인 요청 `sandbox_permissions=require_escalated`)으로 낸다. 샌드박스 안에서 내면 스크립트가 `KITDEV-SANDBOXED:` 를 내고 멈춘다 — 그 줄을 보면 같은 명령을 샌드박스 밖 실행으로 다시 낸다(키트는 MCP 를 띄우고 사내 키트에 닿아야 해서 다른 샌드박스 안에서는 못 돈다).

실행기 `<node>`: 이 세션에서 처음 한 번 아래를 실행하고, 마지막 줄 `KITDEV-NODE:` 뒤의 경로를 쓴다.
- 윈도우: `powershell -NoProfile -ExecutionPolicy Bypass -File "<플러그인 폴더>/scripts/node.ps1"`
- 리눅스: `sh "<플러그인 폴더>/scripts/node.sh"`
- PC 에 Node 가 없으면 사내 키트에서 휴대용 Node 를 받아 쓴다(설치·관리자 권한·재시작 없음). 사용자에게 Node 를 설치하라고 하지 않는다.
- 개발자 PC 는 윈도우와 리눅스를 지원한다.
`.kit/workspace.json` 이 없으면 먼저 `mcp-setup` 스킬을 쓴다.

## 검사 두 갈래
| 감사 | 언제 | 무엇을 | 통과하면 |
|---|---|---|---|
| 개발감사 | `ci` 때마다 | 마지막으로 통과한 커밋과 비교해 **바뀐 파일만** SkillSpector 등 검사 세트로 | 그 커밋을 `test` 로 띄울 수 있다 |
| 배포감사 | `deploy`(mcp-deploy) 때 | 사내 CI(빌드·tools/list·테스트) 통과 확인 + **저장소 전체**를 SkillSpector 등 감시자로 | 관리자가 승인하면 회사 Claude 에 들어온다 |

- 사내 CI 워크플로는 push 마다 뒤에서 돈다. 개발 중에는 기다리지 않고, 배포 요청 때 결과를 확인한다.
- 모드를 고르는 것은 없다(2026-11-25 — 개발자 PC 의 Claude 네트워크는 키트가 통제하지 못하므로).

## 규칙
- MCP 를 손으로 띄우지 않는다(`python -m ...`, `uvx ...`, 직접 만든 JSON-RPC 스크립트 금지). 시험은 항상 아래 `test` 로만 한다.
  - `test` 는 검사를 통과한 커밋인지 사내 서버에 확인받고, 사내 키 저장소의 비밀값을 MCP 환경 변수로만 넣어 준다. 손으로 띄우면 이 둘이 빠진다.
- 가상환경을 직접 만들지 않는다(`python -m venv`·`pip install` 금지). 워크스페이스 `.venv` 는 `test` 가 python3-venv 없이도 만들고, 테스트(pytest)는 사내 CI 가 push 마다 돌린다(배포 요청 때 확인). python3-venv 가 없다고 sudo 설치를 권하지 않는다.
- 검사를 건너뛰는 방법(워크플로 수정·삭제, 강제 push)을 쓰지 않는다.
  - 검사가 틀렸다고 판단되면 사용자에게 알린다.

## 고리
1. 코드를 고친다.
   - MCP 계약: `kit-mcp.json` 의 `name`·`entry`·`egress`.
   - 의존성은 `requirements.txt` 에 `==` 로 고정한다.
   - 툴 표시(HITL): 조회만 하는 툴은 `annotations=ToolAnnotations(readOnlyHint=True)`. 만들기·고치기·지우기·바깥으로 보내기를 하는 툴은 `readOnlyHint=False`, 지우는 툴은 `destructiveHint=True` 도. 배포 때 'HITL 및 킬 스위치 감사자'가 코드와 표시를 대조한다(바꾸는 툴을 읽기 전용으로 표시하면 차단).
     지우기·되돌릴 수 없는 동작을 하는 툴은 docstring 에 무엇이 지워지고 되돌릴 수 없다는 것을 적고, README 에도 그 툴을 경고로 적고, 실행할 때 무엇을 지웠는지 로그를 남긴다(SkillSpector SQP-2 '경고 없는 위험 동작' — 배포 감사에서 필수로 차단).
     관리자가 '서버 측 확인 요구'를 켰으면 바꾸는 툴은 실행 전에 `await ctx.elicit(...)` 로 사용자 확인을 받고, 거절·취소면 아무것도 하지 않는다. 세션이 끝나도 남는 실행(분리 프로세스·데몬 스레드)은 만들지 않는다.
   - 비밀값(API 키·비밀번호)은 코드에서 환경 변수로 읽고, 값은 사내 키 저장소(KMS)에 넣는다.
     ```
     "<node>" "<스크립트>" secret set <환경 변수 이름>
     ```
     - 사용자 PC 에 입력 창이 뜬다(리눅스에 zenity·kdialog 가 없으면 이 PC 안에서만 열리는 브라우저 입력 페이지). 사용자에게 "입력 창에 값을 넣어 주세요"라고만 말한다. 값을 대화로 묻거나 받지 않는다 — 대화에 붙여 넣으면 쓰지 말고 그 창에 넣어 달라고 한다.
     - 이름은 `kit-mcp.json` 의 `secrets` 에 저절로 들어간다.
     - 시험(`test`)과 배포된 MCP 실행 때 그 환경 변수로 들어간다(배포된 쪽은 실행 신고가 통과했을 때만).
     - 무엇이 들어 있는지: `secret list`(이름만).
2. 개발감사를 돌린다(commit·push 뒤 바뀐 파일만 검사).
   ```
   "<node>" "<스크립트>" ci -m "<무엇을 고쳤는지 한 줄>"
   ```
   - 보통 수십 초 안에 끝난다. 위험 점수가 51점 이상이거나 critical 이 있으면 실패다.
   - 실패하면 출력은 다음과 같다.
     - 단계·검사기 목록과 걸린 항목
     - `KITCI-FAIL ...: <까닭>` 과 그 앞 로그
   - 그 까닭만 보고 코드를 고친 뒤 2를 다시 돌린다.
   - 같은 실패가 3번 넘게 되풀이되면 멈추고 사용자에게 상황을 말한다.
   - 내용이 같으면 스크립트가 지난 결과를 다시 쓴다. 같은 코드로 다시 돌릴 필요가 없다.
3. MCP 를 띄워 툴을 부른다.
   ```
   "<node>" "<스크립트>" test tools
   "<node>" "<스크립트>" test call <툴 이름> --args-file .kit/args.json
   ```
   - `tools` 는 툴 목록을 JSON 으로 낸다(이름·설명·inputSchema·annotations). 고친 툴이 목록과 스키마에 맞게 보이는지 본다.
   - `call` 의 인자는 JSON 객체다. 먼저 파일 쓰기 도구로 `.kit/args.json` 에 넣고 `--args-file` 로 넘긴다(PowerShell 은 명령줄 JSON 의 따옴표를 지운다). 인자가 없는 툴은 `--args-file` 없이 부른다. bash 에서는 `--args '{"a": 1}'` 도 된다.
   - 결과는 MCP 응답 그대로(`content`·`structuredContent`·`isError`) JSON 으로 나온다. MCP 서버의 로그(stderr)는 `[MCP]` 를 붙여 함께 나온다 — 오류면 그 줄을 읽고 고친다.
   - 종료 코드: 0 = 성공 · 1 = 툴이 오류를 돌려줌(isError) 또는 MCP 가 실패 · 3 = 개발감사를 통과하지 않은 커밋이라 사내 서버가 거절(먼저 2).
   - 실행마다 MCP 를 새로 띄운다 — 툴 호출 사이에 서버 메모리 상태는 이어지지 않는다.
   - 시험은 뒤에서 돌고 출력이 이어서 나온다. 20분이 지나도 안 끝나면 `"<node>" "<스크립트>" wait` 로 남은 출력을 본다.
   - 고친 툴은 정상 인자 · 경계 인자 · 틀린 인자로 각각 불러 본다. 결과가 기대와 다르면 1로 돌아간다.
   - 바꾸기·지우기·바깥으로 보내기를 하는 툴은 실제로 바뀌는 대상이 있으면 부르기 전에 사용자에게 무엇이 바뀌는지 말하고 확인을 받는다.
   - **skill · plugin**(`kit-mcp.json` 의 `kind`)은 3 대신 인자 없이 `test` 를 돌린다.
     ```
     "<node>" "<스크립트>" test
     ```
     키트가 마켓플레이스에 올릴 모양 그대로 플러그인 폴더(`.kit/plugin/<이름>`)를 만들고 `claude plugin validate` 로 검사한다. `KITDEV-TEST-OK:` 줄에 그 폴더로 Claude Code 를 띄우는 명령(`claude --plugin-dir …`)이 나온다 — 사용자에게 새 터미널에서 띄워 스킬·명령을 직접 써 보게 한다. 스킬은 `skills/<이름>/SKILL.md` 머리(`---`)의 `description` 이 언제 쓰일지를 정하니 구체적으로 쓴다. 새 판을 낼 때는 `kit-mcp.json` 의 `version` 을 올린다.
4. 사용자에게 보고한다.
   - 개발감사를 통과한 커밋, 부른 툴·인자와 돌아온 결과(skill · plugin 은 들어 있는 것과 validate 결과)를 짧게 말한다.

배포는 배포감사(사내 CI 통과 + 저장소 전체 감시자 검사) + 관리자 승인이다(`mcp-deploy`).
