# 사내 MCP 개발 환경 구성

스크립트: `"<node>" "${CLAUDE_PLUGIN_ROOT}/scripts/kitdev.mjs"`
(`${CLAUDE_PLUGIN_ROOT}` 가 치환되지 않았으면, 이 스킬의 Base directory 기준 `../../scripts/kitdev.mjs`)

샌드박스 밖에서 실행: Codex 처럼 명령을 자기 샌드박스 안에서 돌리는 도구에서는 `node.ps1`·`node.sh`·`kitdev.mjs` 명령을 처음부터 샌드박스 밖 실행(Codex: 승인 요청 `sandbox_permissions=require_escalated`)으로 낸다. 샌드박스 안에서 내면 스크립트가 `KITDEV-SANDBOXED:` 를 내고 멈춘다 — 그 줄을 보면 같은 명령을 샌드박스 밖 실행으로 다시 낸다(키트는 시험용 샌드박스를 직접 띄우고 사내 키트에 닿아야 해서 다른 샌드박스 안에서는 못 돈다).

실행기 `<node>`: 이 세션에서 처음 한 번 아래를 실행하고, 마지막 줄 `KITDEV-NODE:` 뒤의 경로를 쓴다.
- 윈도우: `powershell -NoProfile -ExecutionPolicy Bypass -File "<플러그인 폴더>/scripts/node.ps1"`
- 리눅스: `sh "<플러그인 폴더>/scripts/node.sh"`
- PC 에 Node 가 없으면 사내 Git 패키지 저장소에서 휴대용 Node 를 받아 쓴다(플러그인 `tools.json` · 설치·관리자 권한·재시작 없음). 사용자에게 Node 를 설치하라고 하지 않는다.
- 개발자 PC 는 윈도우 11 과 리눅스를 지원한다. 리눅스는 관리자가 처음 한 번 샌드박스 준비(bubblewrap·slirp4netns·AppArmor 프로필)를 해 둬야 한다 — 없으면 setup 이 그 명령을 알려 주고 멈춘다. 그 줄을 사용자에게 그대로 전하고, 내가 sudo 로 대신 하지 않는다.

## 순서
00. 워크스페이스 위치부터 본다(윈도우). 지금 폴더(Claude Code 를 연 폴더)가 내 사용자 폴더 안이어야 한다 — 권하는 곳: `%USERPROFILE%\Desktop\LocalMcpDev\<MCP 이름>` (예: `C:\Users\<나>\Desktop\LocalMcpDev\weather-mcp`).
   - D 드라이브(`D:\…`, `D:\Personal Folder`, `D:\Secure Folder` 포함)·`C:\Knox Drive`·사용자 폴더 밖 C 드라이브(`C:\work` 등)는 안 된다. 샌드박스가 그곳에 쓰지 못해 시험이 멈춘다.
   - 그런 폴더면 setup 을 돌리지 말고 사용자에게 알린다: "이 위치는 MCP 워크스페이스로 쓸 수 없습니다. `C:\Users\<나>\Desktop\LocalMcpDev\<이름>` 폴더를 만들고 그 폴더에서 Claude Code 를 다시 열어 주세요." 폴더는 내가 만들어 줘도 된다(세션 폴더는 사용자가 다시 열어야 한다).
   - 놓쳐도 setup 이 같은 까닭으로 `KITDEV-FAIL:` 을 내고 멈춘다 — 그 줄의 권하는 경로를 그대로 전한다.
0. 회사 프록시는 스크립트가 실행될 때마다 스스로 찾아 쓴다(환경 변수 → git `http.proxy` → 윈도우 인터넷 설정·PAC / GNOME 프록시 설정). 찾으면 첫 줄에 '회사 프록시를 씁니다: …'가 나온다 — 그 줄을 사용자에게 전한다. HTTPS_PROXY·NODE_USE_ENV_PROXY 를 손으로 넣거나 IPv4 우선 같은 우회를 시험하지 않는다. '닿지 않습니다 … 경유/바로 연결' 실패가 나오면 그 줄을 그대로 보여 주고, 프록시 주소를 사용자에게 한 번 묻는다(받은 주소는 `git config --global http.proxy <주소>` 로 넣으면 다음부터 스크립트가 찾는다).
1. 사내 MCP 키트 주소를 확인한다.
   - 사내 마켓플레이스에서 받은 플러그인이면 주소가 이미 들어 있다(플러그인 폴더 `kit.json`). 이때는 `--kit` 없이 실행한다.
   - 그것도 없고 사용자가 주지 않았으며 `.kit/workspace.json` 도 없으면 한 번만 묻는다. 예: `https://mcp.사내도메인`
2. 사내 Git 로그인부터 확인한다(이름을 묻기 전에).
   ```
   "<node>" "<스크립트>" login --check 1
   ```
   - `KITDEV-LOGIN: 로그인돼 있음` 이면 3으로.
   - `저장된 로그인 없음` 이면 사용자에게 묻는다(AskUserQuestion): "사내 Git(키트) 계정이 있나요?" — 있음 / 없음(새로 가입).
     - 없음: `"<node>" "<스크립트>" login --signup 1` — 브라우저에 가입 페이지가 열린다. 사용자에게 가입하고 끝나면 말해 달라고 한다.
     - 있음, 또는 가입을 마쳤으면: `"<node>" "<스크립트>" login` — 로그인 창(Git Credential Manager)이 뜬다. 방금 계정으로 로그인하라고 알린다. 리눅스에 GCM 이 없으면 스크립트가 사내 Git 패키지 저장소에서 받아 둔다(사용자에게 GCM 을 설치하라고 하지 않는다). `KITDEV-LOGIN: 로그인 확인` 이 나오면 3으로.
   - 한 번 로그인하면 그 뒤 setup·ci·test·deploy 는 다시 묻지 않는다(저장된 것이 거절되면 스크립트가 지우고 한 번 다시 묻는다 — 손으로 git credential reject 하라고 하지 않는다).
3. 실행 모드를 사용자에게 묻는다(로그인 뒤, setup 전에 — 이미 이 워크스페이스에서 물었으면 건너뛴다).
   ```
   "<node>" "<스크립트>" mode
   ```
   - 출력의 설명(두 모드의 바깥 네트워크 범위·대가, 관리자 정책으로 바뀜, 언제든 바꿀 수 있음, 바꾸는 말)을 줄이지 말고 사용자에게 전한다. 네트워크 범위는 출력에 나온 값 그대로 적는다(지어내지 않는다).
   - 그다음 묻는다(AskUserQuestion): "어느 모드로 개발할까요?" — 심화 검사(바깥 네트워크 열림) / 기본 검사(허용 목록만). 각 선택지 설명에 그 모드의 네트워크 범위와 대가를 한 줄로 넣는다. 지금 모드(`KITDEV-MODE:`)를 첫 번째에 두고 "(지금 모드)"라고 붙인다. 추천은 붙이지 않는다 — 모드는 사용자가 정한다.
   - 출력에 '기본 검사 모드를 허용하지 않아'가 있으면 묻지 않고, 심화 검사로 진행한다고 알린다.
   - 고른 모드가 지금 모드와 다르면 `"<node>" "<스크립트>" mode deep` 또는 `mode basic` 으로 바꾼다.
   - 끝에 한 줄 덧붙인다: "나중에 '심화 검사로 바꿔줘' / '기본 검사로 바꿔줘'라고 하시면 바꿔 드립니다."
4. 이 폴더가 사내 Git 저장소가 아니면 새 MCP 이름을 정한다.
   - 이름은 영문 소문자로 시작하고 소문자·숫자·`-` 만 쓴다(2~39자).
   - 사용자가 말한 MCP 용도에서 짓고, 정한 이름을 알려 준다.
4a. **진행 목록** — setup 을 실행하기 직전에 이 세션의 할 일 도구(TodoWrite·TaskCreate 등)로 아래 5개를 만든다. setup 출력에 `KITDEV-STEP n/N (p%) <이름>` 줄이 나올 때마다 그 이름을 '진행 중'으로, 그 앞 것들을 '완료'로 바꾸고 사용자에게 `[n/N · p%] <이름>` 한 줄을 전한다. `KITDEV-STEP N/N (100%) 끝` 이면 모두 완료.
   1) 사내 키트 로그인 확인 2) goose·샌드박스 받기 3) 사내 Git 저장소 연결 4) 샌드박스 점검(MXC → srt · MCP 툴 목록 · LLM) 5) 데모 시험
   - `check` 만 다시 돌릴 때는 2·4·5 세 개(출력의 n/N 이 그 기준)다.
   - 할 일 도구가 없는 환경이면 `[n/N · p%] <이름>` 줄만 전한다.
5. 실행한다(워크스페이스 폴더에서).
   ```
   "<node>" "<스크립트>" setup [--kit <주소>] --name <이름> --desc "<한 줄 설명>"
   ```
   - goose·샌드박스·mcp-test 가 워크스페이스 `.kit/` 에 설치된다.
   - 저장소에는 시작 코드와 `.gitea/workflows/kit-ci.yml` 이 들어간다.
5a. **MXC 가 안 되면 srt 관리자 준비(윈도우)** — 샌드박스는 회사 정책 순서대로 MXC 를 먼저 점검한다. MXC 가 안 됐는데 이 PC 에 srt 관리자 준비(전용 계정 srt-sandbox)가 없으면 setup·check 가 `KITDEV-ADMIN:` 을 내고 멈춘다(종료 3).
   - 사용자에게 이렇게 알린다: "MXC 샌드박스가 이 PC 에서 안 됐습니다(까닭: <줄의 괄호 안>). 다음 순서인 srt 샌드박스를 쓰려면 먼저 관리자 PowerShell 을 열고(시작 메뉴에서 PowerShell 을 마우스 오른쪽 → 관리자 권한으로 실행) 아래 명령을 실행해 주세요. 끝나면 '했어'라고 말해 주세요." 그다음 줄의 명령을 코드 블록으로 그대로 보여 준다. 내가 대신 실행하지 않는다.
   - 사용자가 했다고 하면 `"<node>" "<스크립트>" check --sandbox srt` 로 srt 만 점검한다(안 된 MXC 를 다시 기다리지 않는다). 또 `KITDEV-ADMIN:` 이 나오면 아직 준비가 안 된 것이니 명령이 오류 없이 끝났는지 물어 같은 안내를 다시 한다.
   - setup 도중 멈췄어도 저장소 연결은 이미 끝났다 — 이어서는 check 만 하면 된다.
6. setup 은 goose·샌드박스(약 100 MB)를 받는다 — 네트워크 경로에 따라 몇 초에서 수십 분. 이 PC 에서 한 번 받은 파일은 PC 공용 보관함(윈도우 `%LOCALAPPDATA%\mcp-dev-kit\cache`, 리눅스 `~/.cache/mcp-dev-kit`)에 남아 다음 워크스페이스·키트 업데이트 때 같은 판이면 다시 받지 않는다('이 PC 에 받아 둔 것을 씁니다'). srt 가 쓰는 위쪽 폴더 속성 읽기도 한 번 준 폴더는 다시 걸지 않는다. 받는 동안 스크립트가 20초마다 '<파일> N% 완료되었습니다 (받은 / 전체 MB, 분)' 줄을 낸다. 명령이 백그라운드로 넘어가면 그 출력에서 가장 최근 줄을 사용자에게 1분마다 그대로 전한다(예: 'goose 37% 완료되었습니다'). 숫자가 늘고 있으면 멈춘 것이 아니니 끊고 다시 실행하지 않는다 — 1분 동안 1 KB/s 아래면 스크립트가 알아서 이어 받기로 다시 시도하고, 10번 실패하면 오류로 끝난다.
7. setup 은 설치 뒤 **환경 점검**까지 한다(샌드박스 시작 30초쯤 포함, 느린 PC 는 수십 분). 점검은 끝날 때까지 기다리고, 출력이 20분 동안 하나도 안 바뀔 때만 멈춘 것으로 보고 끝낸다 — 1분마다 '…초째 기다리는 중' 줄이 나오면 도는 중이니 끊고 다시 실행하지 않는다. 이 PC 정보(OS·회사 프록시)·사내 키트 로그인·샌드박스(회사 정책 순서대로 MXC → srt — MXC 가 안 되면 srt(윈도우는 5a 관리자 준비 뒤), 둘 다 안 되면 개발할 수 없다(준비 실패). 샌드박스 없이 도는 길은 없다)·점검용 MCP 서버의 툴 목록·LLM 게이트웨이를 실제로 해 보고, 마지막으로 **데모 시험**(키트가 만든 데모 MCP 를 그 샌드박스 안에서 goose 로 띄워 LLM 이 툴을 불러 결과를 받아 오는지)까지 한다.
   - **`KITDEV-READY:` 줄이 나와야만** 사용자에게 "개발 환경이 준비됐습니다"라고 말한다. 설치가 끝났다는 줄(`설치 끝`)만으로는 준비됐다고 하지 않는다.
   - `KITDEV-READY:` 줄 맨 앞 꼬리표(`[MXC]` · `[SRT]`)를 준비됐다는 말 첫머리에 그대로 붙인다(예: "[SRT] 개발 환경이 준비됐습니다 — 이 PC 의 시험은 srt 샌드박스 안에서 돕니다"). 어느 환경에서 시험이 도는지 한눈에 보이게 하는 것이다. 그 뒤로는 이 워크스페이스의 샌드박스가 정해진 것이다 — 플러그인 훅이 매 질문마다 알려 주니 **모든 답변 맨 앞에** 그 꼬리표를 붙인다. 시험·실행(mcp-run)은 정해진 샌드박스 하나로만 돌고 MXC → srt 순서를 다시 돌지 않는다. 정책·키트가 바뀌어 "환경 점검을 다시 해 주세요"가 나오면 이 환경 점검을 다시 한다.
   - 준비됐다고 말할 때 점검 결과를 표로 함께 보여 준다: PC · 회사 프록시 · 샌드박스(MXC / srt — 앞 순서가 안 된 까닭) · MCP 툴 목록 · LLM 게이트웨이 · 데모 시험. 값은 출력 그대로 적는다.
   - 샌드박스가 정책 순서 모두 안 되면 `KITDEV-FAIL` 로 끝난다 — 샌드박스마다 안 된 까닭 줄을 그대로 전한다. 샌드박스를 끄거나 없이 돌리자고 제안하지 않는다.
   - `KITDEV-FAIL: 환경 점검을 통과하지 못해…` 이면 준비되지 않은 것이다. 점검 줄을 그대로 보여 주고 무엇이 안 됐는지 한 문장으로 말한다. 나중에 다시 점검: `"<node>" "<스크립트>" check`
8. 윈도우 MXC 는 관리자 준비가 없다. 관리자 PowerShell 을 열라고 하는 건 5a 의 `KITDEV-ADMIN:` 이 나왔을 때뿐이다. 리눅스에서 setup 이 '관리자가 처음 한 번' 줄을 내면 그대로 사용자에게 전한다.

## 실패하면
- `KITDEV-FAIL:` 뒤의 까닭을 읽고 그대로 고칠 수 있으면 고친 뒤 다시 실행한다. 예: 이름 형식, 다른 저장소에 연결된 폴더.
- 네트워크·로그인·권한 문제는 그 줄을 사용자에게 보여 주고 무엇을 해야 하는지 한 문장으로 말한다.

## 지켜야 할 것
- `.kit/` 는 커밋하지 않는다(.gitignore 에 들어간다).
- 키·토큰을 파일이나 명령줄에 적지 않는다. 로그인은 Git Credential Manager 가 한다.
