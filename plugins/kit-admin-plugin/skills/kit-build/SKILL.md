# kit-build — 키트 서버 설치

## 지금 상황 — 먼저 읽는다
- 이 Claude CLI 는 **관리자가 키트 서버로 쓸 리눅스 서버**에서 돈다. 이 서버에 사내 MCP 개발 키트(사내 Git · 포털 · 검사기 · CI)를 쿠버네티스 위에 올리는 것이 목표다.
- 설치물은 통합관리자가 보낸 **묶음** `mcp-dev-server-kit-v<판>.kit.tar`(수 GB) 하나다. 인터넷에서 받지 않는다. 쿠버네티스(k3s)·이미지도 묶음 안에 있다.
- 도우미 스크립트: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/kitadmin.sh" <명령>`. 아래에서 `KA` 로 줄여 쓴다. 줄 머리 `[ OK ]` 됨 · `[주의]` 볼 것 · `[없음]` 채울 것 · `[실패]` 이대로는 설치 안 됨.
- 비밀값을 대화로 받지 않는다. LLM 공급자 키는 관리자가 **따로 연 터미널**에서 `KA key` 로 직접 넣는다. kitadmin 비밀번호는 정하지 않으면 설치가 만들어 끝에 한 번 보여 준다.
- `sudo` 가 비밀번호를 물으면 Claude 는 실행할 수 없다. 그 줄은 관리자가 Claude CLI 입력 칸에 `! ` 를 붙여 직접 친다(`! cd … && sudo ./bootstrap.sh`).
- 리눅스가 아니면(`KIT-CHECK-FAIL` · 리눅스 아님) 거기서 멈추고 "키트 서버는 리눅스 서버에만 올립니다"라고 말한다. 다른 방법을 찾지 않는다.

## 순서
진행 중에는 단계마다 한 줄로 무엇을 하는지 말한다. 질문은 AskUserQuestion 으로, 추천이 있으면 첫 선택지에 '(추천)'.

1. **요구사항 안내** — 시작하자마자 관리자에게 아래 표를 보여 준다(무엇이 필요하고 무엇을 물을지 먼저 알게).

   | 필요한 것 | 설명 |
   |---|---|
   | 리눅스 서버 | x86_64 · 권장 4 vCPU · 16GB 메모리 · 디스크 넉넉히(묶음 크기의 2배 + 20% 여유) |
   | 설치 묶음 | 통합관리자가 보낸 `mcp-dev-server-kit-v<판>.kit.tar` |
   | 서버 도메인 | 개발자 PC 가 접속할 사내 도메인(IP 안 됨) — 사내 DNS 에 등록 |
   | TLS 인증서 | 그 도메인의 서버 인증서·개인 키·사내 CA(없으면 시험용 자체 서명을 만들 수 있음) |
   | LLM API | 사내 데이터 반출이 승인된 API 주소·모델·키(tool calling 지원) |
   | 바깥 연결 | 서버에서 osv.dev:443 과 LLM API 로 나갈 수 있어야 함(회사 프록시를 거치면 그 주소) |
   | 관리자 권한 | sudo |

2. **서버 점검** — `KA check`. 결과를 표(항목 · 상태)로 보여 준다.
   - `KIT-CHECK-FAIL` 이면 `[실패]` 줄마다 무엇을 고치면 되는지 한 문장씩 말하고 멈춘다(디스크·포트·CPU 종류는 관리자가 고칠 일).
   - 쿠버네티스가 없다고 나오면 "설치 때 묶음의 k3s 를 이 서버에 올립니다"라고 알린다(따로 설치하지 않는다).

3. **묶음** — `KA find`.
   - 폴더(`mcp-dev-server-kit-v<판>`)가 있으면 그것을 쓴다. 여러 개면 가장 높은 판을 추천으로 묻는다.
   - `.kit.tar` 만 있으면 `KA unpack <tar>`(기본 `~/kit` 에 풀고 해시 확인). 끝 줄 `BUNDLE=` 이 묶음 폴더다.
   - 없으면 "통합관리자에게 받은 묶음 파일이 어디 있나요?" 를 묻고(경로 입력) 풀어 준다.
   - 묶음 폴더를 정한 뒤 `KA check <묶음 폴더>` 로 디스크를 다시 계산한다.

4. **질문** — 이미 `setup/` 에 값이 있으면(`KA setup <묶음>` 의 `[ OK ]`) 그 항목은 묻지 않는다. 한 번에 최대 4개씩 묻는다.
   - 서버 도메인: 예 `mcp.회사.com`. 인증서가 이미 있으면 그 인증서의 도메인을 추천으로.
   - 인증서: ① 사내 CA 에서 받은 파일이 있다 → 경로들(server.crt·server.key·ca.pem, .pfx 면 관리자가 직접 풀 명령을 알려 줌) → `KA certs <묶음> <파일>...` ② 없다(시험·PoC) → `KA selfsign <묶음> <도메인>` 하고 "개발자 PC 가 이 CA 를 믿어야 한다"고 알린다.
   - LLM: 공급자(OpenAI 호환 / Anthropic) · API 주소 · 모델 이름. → `KA conf <묶음> LLM_MODEL=<openai/모델 | anthropic/모델> LLM_API_BASE=<주소>`
   - 서버 주소를 인증서 첫 도메인과 다르게 쓸 때만 `KIT_PUBLIC_URL=https://<도메인>`.
   - 회사 프록시: 서버가 바깥으로 나갈 때 거쳐야 하나? 있으면 `KIT_UPSTREAM_PROXY=http://주소:포트`.
   - 사내 PyPI 미러: 있으면 `PYPI_INDEX_URL=<주소>`, 없으면 넘어간다(pypi.org 를 씀).
   - kitadmin 비밀번호: "설치가 만들어 끝에 한 번 보여 주기(추천)" / "직접 정하기"(직접이면 관리자가 `! bash <KA 경로> conf <묶음> PORTAL_ADMIN_PASSWORD=<8자 이상>` 으로 넣게 안내 — 대화에 비밀번호를 받지 않는다).

5. **LLM 키** — 관리자에게 다른 터미널을 열어 아래를 치라고 한다(붙여 넣은 키는 화면에 안 보이고, 이 대화에 남지 않는다). 이미 키 파일이 있으면 `KA key <묶음> --from <파일>`.
   ```
   bash <KA 의 절대 경로> key <묶음 폴더>
   ```
   다 했다고 하면 다음으로 간다.

6. **설치 전 확인** — `KA setup <묶음>`.
   - `KIT-SETUP-READY` 가 아니면 `[없음]`·`[실패]` 항목만 다시 묻거나 고칠 방법을 말하고 4~5 로 돌아간다.
   - 준비되면 정리표(도메인 · 인증서 만료 · LLM 모델·주소 · 프록시 · PyPI · 쿠버네티스: 기존/새 k3s)를 보여 주고 "이대로 설치할까요?" 를 묻는다.

7. **설치** — `KA install <묶음>`.
   - `KIT-INSTALL-NEEDS-SUDO` 면 출력된 `! cd … && sudo ./bootstrap.sh` 를 관리자에게 그대로 주고, 관리자가 쳐서 출력이 대화에 들어오면 그것을 읽는다.
   - 설치는 길다(처음이면 k3s·이미지 넣기로 10~30분). 끊지 않는다. Bash 로 직접 실행할 때는 timeout 을 최대로 두고, 그래도 넘으면 백그라운드로 돌려 끝날 때까지 기다린다.
   - 실패하면 `[실패]` 줄이 무엇을 고치라는지 알려 준다 — 그대로 고치고(관리자 몫이면 관리자에게) 같은 명령으로 다시 설치한다(여러 번 실행해도 안전).

8. **끝난 뒤** — bootstrap 끝 부분의 포털 주소 · kitadmin 비밀번호(처음 한 번만 나옴 — 관리자에게 지금 안전한 곳에 적어 두라고 말한다) · 점검 결과를 정리한다. 이어서 할 일을 알려 준다:
   - 포털(`https://<도메인>`)에 kitadmin 으로 로그인 → '회사 환경'에서 SSO·SIEM 등 · '서버 외부 접속'에서 바깥 허용 확인.
   - 개발자 안내: 포털 '회사 환경' 의 '개발 플러그인 zip 받기' 또는 `kit-status` 스킬의 안내 메일.
   - 상태 점검·문제 해결·업그레이드는 "키트 상태 봐줘"(kit-status).

## 하지 않는 것
- 묶음 안 파일(bootstrap.sh · k8s/ · 이미지)을 고치지 않는다. 막히면 출력 그대로 통합관리자에게 보내라고 한다.
- 인터넷에서 k3s·쿠버네티스·Docker 를 따로 받아 설치하지 않는다(묶음의 k3s 를 bootstrap 이 설치한다).
- 서버의 보안 프로그램·방화벽을 끄라고 하지 않는다. 바깥 연결이 막히면 무엇을 열어야 하는지(osv.dev:443 · LLM API 주소)만 알려 준다.
- 비밀값(LLM 키 · 비밀번호 · 개인 키 내용)을 출력하거나 대화로 받지 않는다.
